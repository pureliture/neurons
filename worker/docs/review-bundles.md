# 맥락 묶음 검토와 일괄 결정

## 목적

사람이 문장마다 승인하지 않고, 같은 프로젝트·brain·범위에 속한 여러 기억을 한 번에 검토하고 승인 또는 반려한다. 검토 기준은 **이 묶음을 기억했을 때 현재 작업 맥락이 잘못되지 않는가**이다. 후보 생성, 사람 결정, 운영 배포는 서로 다른 절차다.

## 사용 순서

1. `memory_review_queue_list`에서 후보와 맥락 영향 분류를 확인한다. 분류는 안내이며 승인 권한이나 내용의 정확성 보증이 아니다.
2. 검토할 후보 ID를 명시적으로 선택해 `memory_review_bundle_read`를 호출한다. 한 번에 1~20개, 단일 `project`, `brain_id`, `scope`만 허용한다.
3. 타입별 묶음에서 기억할 내용, 판단 근거, 다음 행동, 유효 시각과 기존 기억의 충돌 정보를 읽는다. 단순 ID·개수만 검토하지 않는다.
4. 사람이 판단한 뒤 `memory_review_bundle_commit`에 동일한 범위·구성원·`snapshot_token`, 결정, 행위자와 고유 `decision_id`를 보낸다. 반려에는 사유가 필요하다.
5. `canonical_write_performed`와 구성원별 결과를 확인한다. HTTP 성공 또는 `isError=false`만으로 승인 완료를 판단하지 않는다. 제한 도구 거부도 정상 HTTP 응답으로 전달될 수 있다.

예시 입력 형태(합성 식별자):

```json
{
  "project": "example",
  "brain_id": "/project/example",
  "scope": "project",
  "member_ids": ["mem_example_a", "mem_example_b"]
}
```

승인 요청에는 위 필드와 함께 다음 필드가 필요하다.

```json
{
  "snapshot_token": "<bundle read에서 받은 검토 표식>",
  "action": "approve",
  "actor": "<검증된 사람 결정의 행위자 라벨>",
  "decision_id": "<이 결정에 고유한 식별자>",
  "reason": "<선택적 승인 사유; reject이면 필수>"
}
```

## 안전 계약

- 읽기는 DB 기록·모델 호출을 하지 않는다. 구성원은 호출 시 명시한 ID만이다. 읽은 뒤 생긴 후보를 실행 시 자동 추가하지 않는다.
- 기본 commit 권한은 거부다. 기존 review-commit capability와 쓰기 가능한 transport가 모두 필요하다. proposal 허용이나 검토 표식 보유로 승인 권한이 생기지 않는다. auto-accept capability는 따로 유지한다.
- admin 인증은 관리자 접근을 증명한다. `actor`는 감사 라벨이며 사람의 결정을 독립적으로 인증하지 않는다. 사람 검토를 받은 호출자만 commit을 사용해야 한다. 이 기능을 검토 없는 에이전트 자동 승인에 연결하지 않는다.
- 후보와 전체 관련 current 집합을 한 SQL 시점에 읽는다. 기존 기억 대조는 100개로 제한하지 않는다. 프로젝트·brain·scope가 다르면 같은 제목이어도 섞지 않는다.
- 검토 표식은 구성원, 범위, 전체 envelope와 SQL 상태의 해시, 정책 버전과 유효 시각에 서버 서명을 결합한다. `content_hash`가 같아도 제목·요약·typed 정보·출처·권위 상태가 바뀌면 다시 검토해야 한다.
- 일반 pending 후보의 approve/reject만 처리한다. stale/supersede는 기존 전용 절차로 처리한다.
- 같은 주제의 **살아있는** 기존 current 카드 또는 묶음 안의 동일 주제 후보가 있으면 일괄 승인을 막는다. 만료·비활성(권위 아님) 행은 서명 지문에 그대로 포함되어 재활성·변경 시 재검토를 강제하지만, 주제 대조에서는 제외한다(recall 기준과 동일). 중복의 반려는 사유와 함께 가능하다. 제목 정규화 비교는 다른 언어·다른 표현의 의미 중복까지 보장하지 않는다.
- 모든 구성원 검증과 결과의 개인정보 검사를 첫 쓰기 전에 한다. 상태·카드별 감사·묶음 감사·임베딩/그래프 outbox는 하나의 PG transaction에서 반영한다. 뒤쪽 구성원이나 감사/outbox 쓰기가 실패하면 전체를 되돌린다.
- 권위 쓰기 중에는 짧은 공통 잠금으로 writer를 직렬화한다. 사람이 검토하는 시간 동안에는 잠금을 잡지 않는다. 일반 읽기는 계속 가능하지만, 짧은 commit 동안 다른 메모리 writer는 대기할 수 있다.
- 같은 결정 ID와 같은 요청의 재시도는 최초 불변 결과를 반환한다. 뒤에 기억이 stale/superseded되거나 검토 표식이 만료되어도 이미 완료된 결정을 새로 적용하지 않는다. 행위자·결정·사유·범위·구성원·검토 표식이 다른 ID 재사용은 거부한다.

## 검토 표식의 수명과 제한

새 결정에 사용할 검토 표식은 10분간 유효하다. 서명 키는 프로세스 메모리에만 있고 저장하거나 출력하지 않는다. 서버가 재시작되거나 다른 서버 프로세스로 이동하면 아직 결정하지 않은 묶음은 다시 읽고 검토해야 한다. 완료된 동일 요청의 감사 재생은 이 제한과 분리된다. 여러 프로세스에서 검토 표식을 공유하는 기능은 포함하지 않는다.

응답은 내용을 조용히 자르지 않는다. 너무 크면 더 작은 명시적 묶음을 요구한다. 후보별 관측 시각과 유효 시각을 보고 과거 상태를 현재 상태로 오해하지 않는다. 기록의 시각 표시만으로 과거 current 카드가 자동 정리되는 것은 아니다.

## 검증과 운영 경계

단위 검사는 서명 변조·내용/SQL 변경·범위/구성원 변경·만료·개인정보·기본 거부를 다룬다. 실제 PostgreSQL 검사는 전체 rollback, 불변 재시도, 단건/묶음 동시성, 감사와 outbox를 다룬다. 실제 MCP HTTP 검사는 인증·도구 표면·read→commit→새 읽기를 다룬다.

소스 구현과 격리 시험이 운영 활성화의 증거는 아니다. 새 감사 스키마 적용, 이미지 게시, 배포, 관리자 capability 활성화와 실제 사람 검토 연계는 운영 소유 세션의 별도 승인 범위다. 공개 agent 도구는 `brain.resolve`, `memory_candidate_create`만 유지한다.
