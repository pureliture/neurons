# LBrain 교정·지연 수집 합류 설계 감사

검토 기준: source `29a5de42905c43e13834e01893fde47cfb2b5ba4`, 2026-10-25. 이 문서는 제품 코드 수정 전의 조사 결과와 재설계안이다. 운영 데이터를 읽거나 변경하지 않았다.

## 판정과 기존 검증의 한계

사용자가 의도한 작업은 LLM이 발견한 불일치와 변경안을 전달하고, 해당 근거가 아직 수집되지 않았더라도 교정과 이후 세션 수집이 안전하게 합류하는 것이다. 현재의 고정 `registered_json` 정책 구현과 단일 synthetic 카드 HTTP/stdio 검증으로는 이 요구를 충족하지 못한다. **전체 기능의 완료 판정을 철회하고 재설계가 필요한 상태로 본다.** 기존 narrow canary receipt는 그대로 유효하지만 전체 기능 완료의 증거로 사용하지 않는다.

현재 보장되는 것은 지정한 기존 카드에 대한 CAS, 정책 source 검증, successor·supersession·감사·outbox의 authority 트랜잭션과 같은 요청의 재시도다. 아래에서 `정적 확인`은 현재 코드의 구조를 확인한 것이며, 해당 장애가 운영에서 실제 발생했다는 의미가 아니다. `로컬 재현`은 실제 함수에 synthetic 입력을 넣은 결과이며 실제 DB/Neo4j 장애 주입 검증과 구분한다.

| 상세 설계의 범위 | 확정: 현재 처리·안전 검증·감사에 사용되지 않는 설명과 부가 상태를 필수 요구로 늘리지 않는다. 과거 경위 재구성과 불명 상태 표시는 이번 교정의 필수 조건이 아니다. |

근거 내용 보존의 사전검토에서는 기존 source ref 정책·immutable source revision·등록 rollback 검사 45건이 로컬에서 통과했고 실제 HTTP source store에도 immutable write 검사가 있음을 정적으로 확인했다. 이는 저장 계약의 재사용 근거다. 수집 전 근거의 실제 유입, client 관측의 진위 검증, 지연 세션과의 연결까지 통과했다는 뜻은 아니다.

근거의 보존 기간 사전검토에서는 기존 retention이 projection·coverage·archive 조건과 active source revision 보호를 사용하며 관련 로컬 검사 8건이 통과했다. 그러나 PG 교정 결정과 역사 이력이 참조하는 근거를 모든 정리 경로에서 보호하는 연결은 아직 없다. 확정한 보존 정책에 따라 그 참조 보호·동시 참조 추가·정리 중단을 검증해야 하며, 이번 검토에서 live 삭제나 보존 정책 변경은 수행하지 않았다.

과거 조회 사전검토에서는 현재 PG authority 과거 조회가 DB 채택 시각으로 만든 valid_from/valid_to를 기준으로 하고, 관측 시각을 저장하는 필드가 별도로 있음을 확인했다. 관측 시각 하나만으로 실제 유효 구간이 입증되지는 않는다. 사용자와의 검토 결과 과거 실제 상태 재구성 조회는 이번 범위에서 제외한다. 현재 사실 교정, 지연 기록의 역전 방지, 실제 후속 변경 구분, 근거·이력 보존에 집중한다.

요청값과 검증값 불일치 검토에서는 현재 좁은 adapter가 요청한 새 값을 입력받지 않고 source에서 값을 선택하며 지정 필드와 target revision을 제한함을 확인했다. 사용자는 같은 항목에서 검증한 다른 값을 반영하는 B를 선택했다. 범용 LLM 변경안의 입력·비교·반영값 차이 보고는 아직 구현하지 않았다. 이 선택이 다른 사실·환경·항목까지 수정할 권한을 뜻하지 않는다.

기존 기록 부재 검토에서는 현재 교정이 target이 없으면 authority를 바꾸지 않고, 별도의 candidate 생성이 즉시 accepted/current를 만들지 않음을 확인했다. 신규 등록의 의미상 중복 방지는 미검증이다. 사용자는 이번 범위를 기존 기억 교정에 한정하는 A를 선택했다. 검색 실패·검색 범위 잘림·Neo4j 미반영과 실제 기록 부재를 구분하고 신규 생성으로 우회하지 않는다.

자동 교정의 평가 우선순위는 잘못된 교정을 줄이는 A로 확정했다. 기존 candidate 평가에는 근거 누락·충돌·낮은 confidence 등을 보류하는 수단이 있지만, 그 confidence와 OpenRouter 판단 확률은 동일한 값이 아니므로 기존 임계값을 그대로 재사용하지 않는다. 우리 사례에서의 자동 교정 오판율·보류율·미교정율은 아직 미측정이다. 실제 배포 가능 여부와 숫자 기준은 모델·질문·데이터별 검증 결과를 본 뒤 결정한다. 전부 보류해 오판만 없애는 결과는 유효한 기능 검증이 아니다.

일반 수집 갱신 검토에서는 기존 autopilot의 입력 후보·기존 카드 supersession 경로와 PG transaction adapter를 확인했고, 해당 orchestrator의 로컬 단위검사 10건이 통과했다. 이 검사는 store 대역을 포함하며 실제 PG/운영 실행 증거와 구분한다. 사용자는 새 세션이 정상 수집됐을 때도 같은 검증 기준을 통과하면 기존 값을 갱신하는 B를 선택했다. 정기 재검토·미수집 근거를 기다리는 background 처리와는 별개다. 실제 OpenRouter 판단·수집·authority 연동은 아직 실증하지 않았다.

현재 값과 과거 경위 검토에서는 현재 좁은 교정이 target revision과 source를 검사하되 과거 원천 전체를 재구성하지 않고 값을 바꾸는 구조임을 확인했다. source 값 추출·이전 source revision 거부 로컬 검사 2건을 확인했다. 이 결과가 generic 근거의 최신성이나 현재 값의 진실을 보장하지는 않는다. 사용자는 현재 값이 검증되면 갱신하는 A를 선택했고, 변경 경위 설명과 ‘경위 미확인’ 기록도 불필요하므로 제외하도록 정했다. 최신 source라는 전제 자체가 불명확하거나 현재 값에 상충 근거가 남는 경우와는 구분한다.

## 확인한 설계 결함과 미보장

### F1. 교정과 일반 후보에 공통 사실·관측 식별자가 없다 — 우선 해결

`evidence_correction.py:192,224`는 project와 요청 idempotency key로 교정 결정을 만들고, request hash로 successor ID를 만든다. `session_memory/memory_miner.py:166-183`은 source/span/content hash와 추출한 typed payload로 일반 후보 ID를 만든다. 한 경로의 멱등성이 두 경로의 합류를 보장하지 않는다.

로컬 재현에서 같은 source/span/content hash도 추출 payload가 달라지면 서로 다른 후보 ID가 생성됐다. 이는 후보 identity의 현재 동작이며, 이것만으로 의미상 중복이나 충돌이 해결되지는 않는다. 또한 서로 다른 세션의 독립 관측이 같은 사실을 지지하는 경우에도 provenance를 합칠 판단이 필요하다.

`postgres_store/pgvector_schema.sql:13-65`에는 카드 ID 기본 키가 있으나 의미상 동일 사실의 current 집합에 대한 식별·제약이 없다. 단순 unique 제약부터 추가할 사안은 아니다. 먼저 어떤 범위와 시점에서 하나의 사실인지 정의해야 한다.

### F2. 일반 수집·승인 경로가 교정 이력을 반드시 대조하지 않는다 — 우선 해결

`session_memory/autopilot_loop.py:63-100`에서 supersede detector는 선택 사항이고, 대상이 없으면 일반 승인 경로로 간다. `llm_brain_service.py:65-80`의 해당 PG 승인 transform은 structural safety와 pending 상태를 확인하지만 기존 교정과 같은 사실인지를 검사하지 않는다. `memory_evaluation.py:219-236`도 source refs 존재·명시된 conflict·고위험 drift 검사가 중심이다.

따라서 이 경로에 적격 후보가 도달하면 다른 카드 ID의 current가 추가될 수 있다는 것이 정적 확인 결과다. 실제 운영 설정에서 어떤 경로가 사용되는지는 이번 조사로 단정하지 않는다. PG의 전역 authority lock이 쓰기 순서를 직렬화해도 의미상 동일 사실 판단을 대신하지 못한다. 교정 함수만 고쳐서는 이 합류 문제를 막을 수 없다.

### F3. 단일 필드 검증으로 카드 전체를 최신 검증 완료로 표시한다 — 로컬 재현

`evidence_correction.py:352-372`는 기존 카드를 복사하고 허용 필드 및 summary/render를 바꾸며 카드 전체에 `verified_current`를 부여한다. 허용된 `field_path=summary`로 호출할 때 아래 상태가 실제 `_candidate` 함수에서 생성되고 envelope validation도 통과했다.

| 항목 | 재현 결과 |
| --- | --- |
| summary | `기능 상태: ready` |
| typed_payload.status_value | `missing` |
| freshness_state | `verified_current` |

summary만의 주장과 구조화된 상태 값이 충돌한다. 나머지 필드의 예전 근거·확신도를 복사하는 것도 별도 검토가 필요하다. 사실을 식별하는 구조화된 필드와 표시문을 함께 일관되게 생성하고, 검증 범위를 넘는 freshness를 부여하지 않아야 한다.

### F4. 도착 시각과 관측 순서의 적용 계약이 부족하다 — 정적 확인

source 선택은 `resolve_value`에서 `last_seen_at`을 기준으로 한다. 이 시각은 동일 경로의 최근 관측을 고르는 신호지만 서로 다른 세션·branch·환경의 사실 우열을 입증하지 않는다. `steward_decision`은 authority 전환의 `valid_from/valid_to`를 DB commit 시각으로 설정한다. `_authority_filter`의 as-of도 이 유효 구간을 사용한다.

현재 시간 필드 자체가 없다는 뜻은 아니다. 필요한 계약은 늦게 도착한 옛 관측이 현재 값을 되돌리지 않게 하면서, 실제로 새로 검증한 현재 값은 반영하는 것이다. clock skew와 서로 다른 branch에서는 timestamp만으로 순서를 결정할 수 없다. 과거 기록이 처음부터 틀렸는지, 그 뒤 상태가 바뀌었는지의 경위를 반드시 분류하거나 설명할 필요는 없다.

### F5. 검색 지연 처리 일부는 있으나 모든 조회의 교정 가시성은 보장되지 않는다 — 로컬 재현

`graph_first_resolver.py:283-346`은 projection lag가 있으면 graph 결과와 PG hybrid fallback을 합치며, graph 후보의 PG authority도 확인한다. 이 기존 보호를 없는 것으로 취급하면 안 된다.

그러나 `_fallback_cards:542-546`은 embedding client가 없으면 `embedding_unavailable`을 반환한다. 실제 resolver와 기존 synthetic Store/Graph fixture에서 PG current 카드가 있고 graph가 미반영인 상태를 구성했을 때, context는 카드 1건, query는 0건과 위 오류를 반환했다. 실제 Neo4j를 켠 재현은 아니다. 즉 현재의 context/list canary 성공으로 query의 read-your-write를 주장할 수 없다. client가 받은 commit revision을 기준으로 검색 누락과 장애를 명시하는 계약이 필요하다.

### F6. projection 작업의 역순 실행과 최종 current view의 수렴은 별도 증거가 필요하다 — 정적 확인

`postgres_store/outbox_worker.py:217-251`은 leased job과 payload의 identity 일치를 검사하고 adapter 결과를 확인한다. `pgvector_store.py:1978-2012`에는 lease 재회수와 병렬 claim이 있다. 이는 job 무결성과 전달 보호이며 여러 revision이 다른 worker에서 역순 완료되는 경우의 의미적 순서 보장과는 다르다.

이것만으로 graph가 옛 상태로 실제 되돌아간다고 단정하지 않는다. 과거 episode의 보존은 정상일 수도 있다. 검증할 것은 old/new episode가 어떤 순서로 도착하든 최종 current 조회가 PG authority와 일치하며 과거 episode를 새 authority로 해석하지 않는지다.

### F7. 교정 후의 근거 철회·오류 정정·파생 기억 재평가가 정의되지 않았다 — 정적 확인

현재 source 검증은 교정 시점의 source 삭제·revocation을 거부한다. 하지만 나중에 근거가 철회되거나 파서가 결과를 정정했을 때 이미 승인된 교정과 파생 요약을 어떻게 재평가할지는 이 교정 경로에 없다. 일반 GC·source revision 기능의 존재만으로 해결됐다고 볼 수 없다.

`couchdb_source/source_revision.py`와 `current_source_supersession.py`에는 session source set의 manifest와 revision 활성화가 이미 있다. 이를 재사용하되 source revision의 일관성과 사실 resolution의 일관성을 구분해 연결해야 한다. 기존 계약을 무시한 별도 session 저장소를 만들지 않는다.

## 공통 합류 계약 제안

이 절은 구현된 기능의 설명이 아니라 재설계안이다. 기존 source revision·PG stewardship·outbox를 재사용하고 아래 의미 계약을 연결한다.

### 구분해야 할 식별 축

| 축 | 의미와 주의점 |
| --- | --- |
| 관측 | provider/session/event anchor, 검증된 원천 artifact revision, hash와 관측 범위. 수집 batch·chunk와 분리. 같은 세션에도 서로 다른 관측이 있으므로 session ID만으로 dedup하지 않음 |
| 주장 | 관측에서 추출한 subject/predicate/value 및 context·유효 범위. 하나의 관측이 여러 주장을 지지하고, 하나의 주장이 여러 관측으로 지지될 수 있음 |
| 사실 범위 | project/repo와 필요한 branch/environment/subject/predicate/time 범위. claim key는 이 범위를 일치시키는 수단이며 일반 문장의 의미 동일성을 자동 해결하지 않음 |
| 교정 요청 | LLM의 target+expected revision, 틀린 주장, 변경안, 불일치 설명, evidence refs 또는 수집 전 검증 가능한 관측. 이 설명은 판단 대상이지 권위 자체가 아님 |
| 결정 | 해당 관측·주장 집합과 정책 버전에서 왜 attach/replace/conflict 등을 택했는지 기록. current view는 이 결정으로부터 구성 |

관측 identity는 진짜 event anchor 또는 검증된 source revision에 결속해야 한다. 임의 client가 붙인 session/turn 번호만 신뢰하지 않는다. 안정적인 anchor가 없는 입력은 이후 원천과 동일하다고 미리 확정하지 않고, 별도 관측으로 보존한 뒤 검증된 alias를 연결한다. 문장 유사도나 hash 하나는 의미상 동등성의 충분조건이 아니다.

### 공통 처리 흐름

1. 교정·세션 intake·backfill·재추출 모두 원천의 범위와 권한을 확인하고 관측을 등록한다. evidence는 먼저 영속화하며 새 중앙 저장소를 임의로 추가하지 않는다. Mac thin client에 원문 전송·server build 책임을 옮기지 않는다.
2. LLM의 변경안 또는 miner의 추출을 구조화된 주장으로 정규화한다. 근거가 새 주장을 실제 지지하는지 검증한다. 의미 검증이 불확실하면 pending/conflict로 남긴다. metadata 검사만으로 진실이 증명됐다고 처리하지 않는다.
3. 도착 시각 대신 source revision ancestry·같은 세션의 검증된 event 순서와 대상 환경을 확인한다. 서로 다른 branch나 불명확한 시계는 부분 순서이며 억지로 전순서를 만들지 않는다. 과거 경위를 모두 복원하는 대신 현재 값이 실제로 검증됐는지와 옛 관측의 잘못된 재적용 여부를 확인한다.
4. 공통 resolution 경로가 같은 사실 범위의 current와 관련 관측을 대조하고 결과를 결정한다. 기존의 일반 승인·재생 경로가 이 검사를 우회하지 않도록 연결한다.
5. 검증 대상 revision과 claim 범위를 authority lock/CAS 안에서 다시 검사하고, assertion 전환·감사·lineage·outbox를 PG에서 원자 기록한다. source 저장소와 PG가 자동으로 하나의 트랜잭션이 된다고 가정하지 않는다. 이미 영속화한 immutable evidence 참조를 commit하고 crash 뒤의 비권위 orphan을 처리한다.
6. 교정 응답은 자신의 결정, 현재 head, authority commit revision, projection 상태를 구분한다. 새 조회에는 최소 commit revision을 전달할 수 있어야 하며 기존 prompt까지 소급 갱신했다고 주장하지 않는다.

### resolution 결과

- `noop_duplicate`: 같은 관측·동일 해석이 이미 반영됐다.
- `attach_evidence`: 독립 관측 또는 나중 확인된 원천을 기존 주장에 연결한다.
- `retain_history`: 비교 가능한 과거 사실로 보존한다.
- `replace_current`: 검증된 현재 값으로 successor를 만든다. 전후 값·검증 근거·처리 시각을 보존하며 과거 변경 경위나 그 불명 상태를 별도로 생성하지 않는다.
- `disputed`: 같은 범위·유효 구간에 양립 불가한 근거의 우열을 판단할 수 없다. 도착 순서로 하나를 확정하지 않고 단정적인 최종 값을 반환하지 않는다.
- `pending_evidence`: 근거 도착·완전성·검증을 기다린다. timeout과 재시도 가능 상태를 노출한다.
- `reject`: cross-scope·변조·권한·지원 범위를 위반했다.

건별 사람 승인을 기본 흐름에 다시 넣지 않는다. 자동으로 확정 가능한 근거는 적용하고, 확정할 수 없는 경우 근거와 이유를 명시한다. “LLM이 말한 대로 무조건 교정”과 “서버의 고정 JSON 대응표만 허용” 사이의 의미 검증 계약을 별도 구현해야 한다.

### 사용자 결정: 코드와 OpenRouter 판단 모델의 결합

코드로 확정할 수 있는 조건을 먼저 처리하고, 남은 의미 판단에 OpenRouter 판단 모델을 사용한다. 모델 후보와 역할 분담은 사용자 지시로 정해졌다. 초기 기본 모델은 `perplexity/pplx-decider-flash-v1.2`, 비교 검증 후보는 `respan/span-02`로 선택한다. 자동 적용 기준은 실제 사례 검증 후 정한다.

- [`respan/span-02`](https://openrouter.ai/respan/span-02/providers)
- [`perplexity/pplx-decider-flash-v1.2`](https://openrouter.ai/perplexity/pplx-decider-flash-v1.2/providers)

선택 근거는 2026-10-25 공식 표시 기준 두 모델의 입력 요금이 모두 100만 token당 $0.01인 반면 Decider Flash V1.2의 context 한도는 262,144 token, Span-02는 131,072 token이라는 점이다. 같은 입력 요금에서 관련 근거를 함께 비교할 수 있는 용량을 우선한 초기 선택이며, 긴 입력 전체를 항상 전송하거나 정확도가 더 높다고 가정하지 않는다. 우리 사례에서의 정확도 우위는 아직 검증하지 않았다. 기본 모델을 고정해 우선 검증하고, 자동으로 다른 모델로 전환하지 않는다.

2026-10-25 OpenRouter 공식 모델 설명에서 두 ID와 구조화된 판단 출력을 확인했다. 연결은 OpenRouter Decisions API 계약으로 검증한다. 일반 chat completions 호출과 응답 parsing을 전제하지 않는다. 이번 문서 반영은 API 실호출이나 우리 데이터에서의 정확도 검증을 뜻하지 않는다.

| 담당 | 처리 범위 |
| --- | --- |
| 코드의 사전 검사 | exact observation ID 중복, 확정된 scope·revision·인과 순서, source 존재·hash·접근 권한, 이미 정규화된 주장 값의 비교 |
| 선택한 판단 모델 | 표현이 다른 주장들의 의미상 동일성, 근거의 변경안 지지 여부, 검증된 현재 정보로 갱신 가능한지 및 충돌/무관/판단 불가의 구분. 과거 변경 경위 설명이나 분류는 요구하지 않음 |
| 코드의 후속 처리 | 응답 형식·허용 결과·검증된 적용 기준 확인, 최신 target 재확인, CAS·원자 저장·감사·재시도·projection 관리 |

36개 시나리오마다 모델을 호출하지 않는다. 결정 가능한 입력은 코드로 끝내고, 의미 해석이 필요한 관련 주장·근거 집합에만 좁은 질문을 보낸다. 기존 추출 결과와 저장된 판단도 재사용한다. 두 모델을 매 요청마다 모두 호출하거나, 한 모델의 낮은 확률을 다른 모델의 답으로 자동 대체하는 절차는 정하지 않았다.

같은 판단의 재사용 키에는 정규화한 입력·근거 revision·scope·질문 버전·정책 버전·모델 ID를 결속한다. 모델 응답과 가능한 제공자/버전 정보를 함께 보존한다. 근거가 추가되거나 정책이 바뀌면 새 판단을 기록한다. 모델 ID 고정이나 응답 저장만으로 모든 의미 판정이 정확하거나 모든 입력 순서가 수렴한다고 주장하지 않는다. 앞서 정한 순열·충돌 검사도 필요하다.

모델의 높은 확률만으로 자동 반영하지 않는다. 정답이 있는 실제 유형별 사례로 잘못된 교정 비율·판단 보류 비율·순서에 따른 결과 변화를 비교해 모델별 적용 기준을 정한다. 근거 부족·응답 오류·timeout·판정 불확실은 authority 변경 없이 명시적 보류/실패로 남긴다. 조건을 통과한 교정에는 건별 사람 승인을 추가하지 않는다.

## 재설계에서 유지할 불변조건

1. 같은 원천 관측·정책·context에 대해 **교정 먼저/수집 먼저/재시도/재생 순서가 달라도 처리가 끝난 의미상 결과가 같아야 한다.** audit append 순서나 모든 내부 ID가 같아야 한다는 뜻은 아니다. 비교 불가능한 상충 근거는 어느 쪽이 먼저 와도 disputed로 수렴해야 한다.
2. 과거 snapshot의 늦은 도착이 이후 상태를 되돌리지 않는다. 반면 실제로 이후 발생한 rollback은 과거 값과 같아도 새 관측으로 취급한다.
3. 관측과 assertion을 분리하고 provenance의 독립성을 보존한다. 자기 재인용을 새 독립 증거로 승격하지 않는다.
4. 같은 사실 범위의 충돌을 모든 authority writer가 확인한다. 카드별 요청 멱등성이나 PG 직렬화만으로 의미상 중복 해결을 주장하지 않는다.
5. 한 필드의 교정이 검증하지 않은 다른 필드의 freshness·confidence를 올리지 않는다. 표시문과 구조화된 값은 항상 일치해야 한다.
6. 관측·반영 시각과 확인 가능한 작업 순서는 지연 수집의 역전 방지에 사용한다. 과거 변경 경위를 추정하거나 ‘경위 미확인’ 설명을 필수로 만들지 않는다. 특정 과거 날짜의 실제 상태 재구성 조회는 이번 범위에서 제외한다.
7. graph·vector·cache는 authority를 역전시키지 않는다. 재시도·역순 투영 후에도 새 조회의 commit revision 기준 가시성을 검증한다.
8. 근거 철회·parser 정정·권한 변경 시 영향받은 assertion과 파생물을 찾을 수 있어야 한다. 철회가 자동으로 이전 값을 참으로 만드는 것은 아니다.
9. commit 뒤 오류는 미반영 응답과 구분하고, retry가 과거 successor를 다시 current로 만들지 않는다.
10. 검증 단계와 범위를 보고한다. 단위 함수·실제 PG·실제 graph·LLM 운영 workflow는 서로의 증거를 대체하지 않는다.

## 검증 계획과 변경 순서

1. **의미 계약 확정:** 식별 축, context, 현재 값 검증, 지연 수집의 순서·충돌 판정과 응답을 스펙에 먼저 확정한다. 이 문서의 제안은 아직 구현 완료나 승인된 최종 API가 아니다.
2. **재현 결함 수정:** summary/payload 일관성과 field별 검증 범위를 고치고 재현 입력을 회귀 검사로 남긴다. 현재의 좁은 canary만 반복해 완료 처리하지 않는다.
3. **write 경로 합류:** correction·intake·autopilot·backfill이 같은 resolution 검사를 거치도록 연결한다. 일반 승인 경로 우회와 같은 claim의 다른 카드 ID 동시 승인을 검사한다.
4. **순서·재생 검사:** C01~C36을 상태 전이표로 연결한다. 관측·정책이 같은 경우 입력 순열, 중복 횟수, chunk/parser 변경과 crash 위치를 바꿔 최종 assertion·근거 집합·conflict·supersession의 의미 동등성을 검사한다. 실패한 원천을 임의 skip해 통과시키지 않는다.
5. **실제 배포 proof:** 격리 project에서 실제 LLM이 아직 수집되지 않은 관측을 교정 요청으로 제출한다. 실제 session ingest/miner를 지연시켰다 재개하고, 반대 도착 순서·의도적 rollback·상충 agent·근거 철회·Neo4j/embedding 정지·worker 역순 재생을 수행한다. 동일 query/context/list와 authority/audit 전후, projection 수렴, 정리까지 검증한다.

전체 graph 지연을 항상 전량 PG scan으로 덮는 식의 임시 해결도 피한다. correction receipt의 정확한 target/head를 확인하는 경로와 일반 검색에서 관련 미투영 사실을 찾는 경로를 구분하고 bounded 조회·분명한 gap·수렴을 함께 설계한다.
